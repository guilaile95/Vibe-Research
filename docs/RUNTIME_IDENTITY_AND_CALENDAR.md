# 运行身份与交易日历维护

## 三件事不能混同

健康接口响应、源码已合并、当前机器运行该版本，是三个不同事实。
后端 `/api/runtime-info` 是启动时快照；Agent Runtime `/runtime-info` 也是启动时快照；
前端生产构建提供 `/vibe-build.json`。它们不读取模型凭据或持仓，也不证明模型连通。

在已授权的目标机器，使用只读命令比对明确的完整提交：

```sh
python tools/verify_runtime_identity.py --expected-sha <完整40位提交>
```

非默认端口用 `--backend`、`--frontend`、`--agent-runtime` 指定显式 loopback HTTP origin。
若后端已有访问密钥，只从现有 `VR_API_KEY` 环境读取，不放命令行、不打印。
检查不启动/重启服务、不更改配置、不跟随重定向、不使用网络代理、不调用模型。
返回值：0 为三个源码坐标一致，1 为坐标或工作区状态冲突，2 为证据不足。
缺失/未知身份不能冒充匹配。前端开发服务器有 HMR，因此即使启动坐标相同也返回未验证；
应使用固定生产构建验收，不把开发服务健康 marker 当部署证明。

源码归档不应继承外层 Git 仓库身份。Linux 安装包的 manifest 记录源身份与逐文件哈希；
当前 Linux 安装包也不包含 .git，故后端与 Agent Runtime 的运行身份采集仍返回 unknown；
manifest 的 source_identity 和前端构建身份并不向这两个运行时提供身份，不能证明三服务 SOURCE_MATCH。
先运行安装包既有 `verify`/启动完整性检查，保留包哈希。旧包缺身份时同样保持未知，
不要手工填写一个 SHA 来制造通过，也不要为更新版本自动覆盖用户工作区。

实际部署验收还需：确认目标机器和目录、隔离用户数据、备份与普通代码回滚策略、
运行核心只读流程、检查模型/数据源的明确验证状态。三坐标一致本身不是完整上线验收。

## 日历是有期限的可信资料

`/api/calendar-status` 只读暴露已验证范围、剩余日数与状态；设置页展示同一结果。
距覆盖结束90日内为 EXPIRING，超过范围为 EXPIRED，坏资料为 INVALID_ARTIFACT。
这些状态不修改交易日，也不把工作日推断成交易日。

截至本次维护，仓库官方一致性资料只覆盖2024至2026年。2026年10月24日核查沪深交易所
公告入口，未取得可核验的2027年度双方正式休市公告；不得用第三方日历或猜测填充。
2027范围仍是客观待补资料，不记作已验证。

官方入口：
- https://www.sse.com.cn/disclosure/dealinstruc/closed/list/
- https://www.szse.cn/www/disclosure/notice/general/

获得下一年度官方资料后：分别保存SSE/SZSE来源与日期，核对一致性、补充可信数据，
同步严格元数据校验与跨年测试；保持未知、非交易日、已完成交易日的区别。
预测EPS的年份标签也必须与来源字段一致；不自动把2026字段改称2027。

## 接管入口

先读 AGENTS.md、CURRENT_STAGE.md 的来源角色，再读取实时 Git 分支、PR、CI。
历史 Draft 可能已通过另一条普通合并进入 stable；用祖先/树证据判断，不能据 open 标记重复施工。
历史 Notion/Issue 快照保留日期，不把它们当作当前运行版本。不要建立第二套实时状态数据库。
